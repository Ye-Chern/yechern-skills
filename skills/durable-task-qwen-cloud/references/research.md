# 研究任务的证据接口

以下以数学为例，也适用于代码或调查。先确定对象、证据、验收、失效条件、用户偏好。没有对任务作出贡献的管理字段可以省略。

- 严格证明：假设、命题、关键推导、引用和适用域。有限样例不能升级成全称证明。保留可复用的估计函数及位置/参数条件；“这个统一粗估计卡住”不等于“所有加权估计都卡住”。
- 有限穷举：完整域、实际覆盖单元、总数、重复/缺口、truncated、生成器及终态校验。阴性结论须明确 `exhaustive` 和边界；cap、超时、候选前缀的零命中只能记录该范围的零命中。所有搜索层都完整才可在那个有限域说无解。
- 数值探索：精度、容差、实例、算法和原始输出。候选反例先独立重算并检查语义，再撤回上游；候选最优值不能当严格常数。对反复使用的数值原语先做便宜的不变量、已知闭式输入、独立实现对拍；检查代码是否真正执行指定分支。
- 文献：实际读过的原文/必要摘录、URL/版本/章节；二手导航只作线索。检索失败记录覆盖，不推出不存在。不联网时写未核查，不编造论文或引用。

每个关键结论最少保存：ID、类型、scope、依赖、原始结果位置、验证方法/结果/限制。完整性可以这样记录（填真实值）：

```json
{"claim_type":"finite-exhaustion","completeness":{"exhaustive":false,"domain":"explicit finite input domain","completed":"units 0..4","expected":"units 0..9","truncated":0,"limits":"remaining units not run"}}
```

`exhaustive=true` 要有整个域的验收依据；这个字段不是脚本自动认证。`truncated=0` 只说明该引擎报告未截断，还须核对外层是否漏分块、报告是否来自正确版本。

稳定证据通常绑定输入、生成器/版本、冻结原始 stdout 和校验器；滚动日志只作进度，终态日志另存。需要修改生成器语义时用新名字/版本或保留旧源码，更新复现命令。不能让同名新工具为旧结果冒充来源。

报告中的关键数字/范围先定位原始日志或机器数据。必要时生成小核对脚本，从源数据独立重算，而非仅断言报告里有某句文本。哈希审计不检查手写数字；把命令 exit 0 等同于全部语义正确会漏掉边界约定错误，例如最小值扫描遗漏 0。

定向核对新证明的关键逻辑桥梁：某个对称性是否真的蕴含全部所需条件；“等价”是否覆盖原问题的完整函数类（例如均值零子类到一般函数是否少了常数方向）；一次粗估计失败是否被夸大为所有同类方法不可能。符号证明中，报告的参数区间/端点与执行代码、根证书须一致，分母和样点定号也需依据。能复核主结论而证明文字有错时，分别记录有效结论与需要修正的理由，不把错误理由继续作为依赖。最终报告的当前结论/障碍随已验收结果更新；过时说法只能留在有时间和状态的历史段落。
