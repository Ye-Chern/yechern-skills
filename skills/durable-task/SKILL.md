# Durable Task — 长任务结构与恢复

把工作组织成可继续求解的问题，而不只是压缩聊天。用户的好想法、好数据、好结构分别落为任务契约、可定位的证据、可检查的依赖关系。成功标准是恢复后能作出正确的下一步，而不是记忆文件越来越多。

## 开始或恢复

1. 先识别是否已有恢复入口。优先复用项目的 README / 状态 / 计划 / 日志，不重建平行真相源。恢复中保留原目标，合并用户的新约束。
2. 为本任务写一份短契约：目标与品味（有样例就链接样例）、验收条件、授权范围、数据来源、关键不确定性。缺少决定性输入时早问；能独立推进的部分继续。不要把主观目标伪装成客观事实。
3. 选择本任务的验证方式，读 [profiles.md](references/profiles.md)。默认采用 Codex 的文件工具和现有专业 skill；Specialization 是任务接口的专门化，不是换模型、训练权重或开启常驻进程。
4. 新建记忆时默认放项目 `work/task-memory/<task-id>/`；已有项目使用既有路径。轻量任务只需契约、当前状态、追加日志；当依赖、撤回或文件漂移重要时，读 [protocol.md](references/protocol.md)，用 `scripts/task_memory.py` 建立账本。脚本只用 Python 标准库，不安装依赖。
5. 本技能脚本模式恢复：先`resume`重建短入口，再读契约并按ID取回相关证据；无关历史只统计，需用时查询。完成核查需要时用`audit --strict`，区分完成声明与有验收记录的完成。其他工具账本先核对格式；不兼容时按原协议或手工恢复。旧capsule不当现况。
6. 接收恢复包、换环境、准备中断或管理长进程时，按需读 [handoff.md](references/handoff.md)。核对入口所指材料和产物的用途、版本与完整性；旧路径、PID、窗口预算和“完成”标签不能替代当前检查。

## 推进一段有意义的工作

- 从当前前沿选一个动作：解除共享阻断、验证最脆弱的前提、或完成可验收的产物。优先选择能区分候选解释的实验，避免把“多收集一点材料”当默认进展。计划保留少量下一步，可以重写；被否定的理由留在历史里。
- 按完成标准检索数据；保留关键输入、工具原始结果或最小可复现材料，给来源版本、符号/章节/锚点和适用范围。只保存影响后续决策的内容，不保存隐藏推理逐字稿，也不复制全部聊天。
- 大结果留在可取回的文件中，先读索引、覆盖范围与当前相关部分。摘要或投影注明省略范围，取不到全文时不冒充完整；滚动进度与已验收的冻结证据分开。
- 将证据、结论、决定和任务分开；关键依赖用稳定 ID 连接。`accepted` 是在记录的 scope 内验收，绝不是全局真理。重要结论先读证据，再用适合领域的验证；命令退出成功不等于语义正确。外部或自己的“已完成”声明都需要具体依据，但不要无理由重复已经足够且仍有效的检查。
- 文件变化、证据撤回或上游修订使下游进入复核状态。不能因路径相同或新检查通过就自动沿用旧结论。手工模式也必须沿依赖追查。
- 出现新决定、反例、撤回、用户约束变化、阶段产物或切换分支时立即保存。不能依赖能够预测何时发生压缩。用短恢复入口写明当前动作、未解问题、不能重走的坑及证据指针；每轮工具调用都做记忆管理会浪费注意力。
- 每个重要阶段问一次：这一局部成果解除了整体的哪项依赖？是否存在另一个分支能复用？若得到新的连接，先作为候选记录，验证后再进入当前状态。“Eureka”不是验收条件。

## 恢复与完成的硬边界

恢复后须能回答：现在要交付什么、哪些事实可用、哪些被撤回、凭什么、下一步如何验收。答不出来就定向读取相关记录，不能靠摘要补全缺失事实。

脚本的哈希只检验字节漂移，依赖图只检查已声明的边；它们不检验结论的正确性、未知依赖或授权。数据库事务保护账本写入，不保护外部产物或磁盘备份。需要时保存独立交付快照并比对；不擅自恢复覆盖用户文件。

交付时按契约验证产物，报告已完成与尚未验证的范围，并留下可继续工作的入口。文件只有“存在”不够。skill 不创建 goal、自动化、子代理或外部消息；这些仍按用户授权及当前系统规则执行。长任务不意味着被动等待或无限循环。

中断后先核实已落盘或已发生的结果，再决定重做哪一步；未知结果不等于失败或从未执行。交付收尾核对本任务仍需的进程与未完成项，不把整段工作盲目重跑。

## 持续改进接口

遇到真实恢复失败、重复劳动、误信旧证据或管理成本过高时，读 [evolution.md](references/evolution.md)，在本技能的 `state/IMPROVEMENTS.md` 追加可复现观察。依用户对本技能的既有授权，可实施窄范围、可回退的改进；没有授权时记录提案。

先确定失效机制，再做最小修改和相应重放。区分建议、已实施、已验证、已回退。保留修改前的相关文件和回退方式，不把单次成功写成普遍效果；不要积累万能规则或改变其他 skill、全局配置与授权边界。

设计取舍见 [research.md](references/research.md)，仅在需要时读取。操作和改进日志各自按需读取，避免每次加载全部参考材料。
