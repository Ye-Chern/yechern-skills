# 实践改进协议

先定位失效在数据、解释、索引、更新、恢复、验证或管理负担，再选择最小修正。

## 可调用接口

用户可以说：`使用 $durable-task 复盘这次恢复失败，并改进 skill`。使用过程中可记录实际观察；修改技能前须确认当前授权。既有任务中的授权不随技能分发。

日志：本技能 `state/IMPROVEMENTS.md`。任务结论、数据、偏好留在各自任务里；跨任务通用化要有依据，不复制私人数据进技能包。

每条追加：
```text
ID / 日期 / 状态：proposed | implemented | validated | reverted
观察：实际输入、输出、产物；区分实测与预期
失效机制：可能只是任务特例
变更：文件、适用任务、前版本及哈希
验证：重放失败场景；必要时加相邻反例；未覆盖处
成本：读取/写入量、重复探索、错误或额外步骤；没测就写没测
回退：修改前文件位置、恢复方式
剩余问题：下一次实践应检验什么
```

## 修改纪律

1. 先追加 proposed；修改前把涉及文件复制到 `state/versions/<change-id>/` 并记录原哈希。
   备份的技能入口用 `SKILL.md.bak` 等非入口名，清单记录原路径与备份路径，避免递归发现把旧版注册为另一个skill；回退时按清单恢复原文件名。
2. 最小修正尽量放相关参考或脚本。若改触发范围，也测试不该触发的请求。
3. 运行 skill-creator quick_validate（若可用）；脚本修改必须重放实际失效场景。验收观察行为，不匹配规则文字。
4. 有隔离资源且允许委派时可做独立恢复演练：只给 skill、契约、入口和原始材料，不给预期答案。没有授权就在单代理内做确定性破坏/恢复测试，明确这不能验证模型行为。不自行调用收费模型、路由服务或创建用户可见新聊天。
5. 追加记录说明 proposed → implemented → validated，旧记录不改。不成功就追加 reverted 并还原相关文件。版本号写日志，不伪造产品的版本机制。
6. 若交付包、研究说明或任务入口受影响，一并更新，避免安装版与说明版不一致。

## 目标

降低遗漏用户条件、误用撤回结论、漏失效依赖、重复探索和恢复成本。可以测恢复正确率、错误 accepted 数、读取字符数、工具调用和管理耗时；没有实测不要填数字。

不追求日志长度、节点数、文献数或模板覆盖率。规则只增成本且无可复现收益时简化/回退。文件哈希过敏可用更小的证据快照缓解，不能仅忽略告警。
