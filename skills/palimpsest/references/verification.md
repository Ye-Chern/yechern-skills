# 数学验收与证据边界

验收对象是固定陈述的一个版本；验证工具只是手段。没有一条全局硬度序能解决不同范围的证据冲突。

## 最小证据记录

每项重要检查记录 `evidence_id`、`target_id@revision`、完整假设/范围、输入或代码版本、方法/命令、实际结果位置、未覆盖项与信任边界。重要来源记录作者、标题、版本/年份、URL、章/定理/页码、相关定义，以及本题到来源假设的映射。读不到全文就标“仅检索线索”，不能假装核实。

由主 agent 判定该记录支撑什么。不得让被验证的候选修改验收规范；修验证器 bug 要单独记录原因、修改版本并重跑受影响检查。

## 计算证据

**抽样与有限影子**：记录范围、生成方式、容差/精度；通过只记实验支持。未搜到反例只说明该搜索域/方法未命中。趋势拟合不能建立渐近式；有限递归深度不能建立一般终止性。

**有限穷举**：可以证明真正有限的命题，前提是证明枚举无遗漏、对象合法、判定函数与题意一致、所有状态完成。给实例数与覆盖论证，不用“跑了很多”代替完备性。只有证明了归约到这个有限域，才能推广到原目标。

**精确计算与符号系统**：核查域、符号假设、分母非零、分支切割、积分/极限的适用条件。`simplify` 返回 0 不替代这些前提；转换和归约也应在数学论证中说明。精确代数恒等式可闭合相应义务，不能认证同稿未被检查的分析、几何或无穷组合部分。

**数值反例**：先查定义域、约束、边界和符号约定。浮点越界需要误差界、区间算术或精确 witness；高精度重复增强可信度，但本身不是严格误差界。非法 witness 不否证命题。区间算术认证须包含全域覆盖及误差控制，不能只因库名叫“区间”就认为一般证明通过。

**脚本证书**：检查代码做了什么，不信自打印的标签。`print('HARD_ACCEPT')`、硬编码预期值、两个实现共享同一错误公式、assert 与生成器复用同一逻辑，都可能没有独立检验价值。对关键算法证书用独立推导/小手算样例/不同实现核查；不用为了仪式重复全部计算。

超时/缺库/网络失败/运行错误是未验证。程序 assertion 失败还需区分实现 bug、非法输入与合法数学反例。

## 自然语言证明

完整展开最关键的推理，而不是把每句平凡代数写长。依赖图应是非循环的；每个未显然节点给证明或真实可适用来源。优先检查：

- 量词次序、统一与逐点估计；同一个对象是否贯穿推论；索引、符号、方向。
- 引理是否比主结论更强却无独立证明；是否偷换定义或把目标写入前提。
- 极限/和/积分互换是否有控制；最小值/最优对象是否真的达到；选取能否保持全部要求。
- 有限构造升级为无限对象时，是否有相容性、紧性或有效递归；不能用数个有限成功样本代替。
- 文献原定理的拓扑、正则性、有限性、可数性等前提是否满足；相同术语是否相同定义。
- 分支是否穷尽，递归量是否严格下降，新增前提是否一致且有标准实例。

独立审查须给“已核查哪些义务、最早错误/缺口在哪里、剩余不确定性”。审查者可给严谨逻辑反驳，即使没有工具。未能识别错误不等于全部义务闭合；重要未解异议不能用多数票消除。

经过完整文本证明和审查，可记 `proved-informally`，表示负责人认为自然语言论证闭合，仍有模型相关错误风险。只有部分文本或候选思路通过时保持 `candidate`。用户明确要求机器认证时，自然语言闭合是阶段结果。

## 形式化证明：双重检查

1. **语义对应**：固定源命题、正式声明和定义；逐项核查对象、量词、域、结论、隐藏类型类前提、强弱、空真/不一致和标记的新增公理。需要归约时明确证明其方向。宜用独立短 specification 核查目标，支持时可用 Comparator；工具不可用不假造检查。
2. **证明产物**：记录 Lean/Isabelle 与库的实际版本/锁定配置，构建完整目标及传递依赖；保存实际命令、退出状态、日志、源码版本。抽取孤立片段通过不认证整项目。读取目标的真实声明与公理依赖，不能仅 grep 无 `sorry`。

Lean 的具体检查：对最终目标与关键模块执行实际构建，并获取 `#print axioms <目标>`；检查传递依赖的 `sorryAx`、额外公理和依赖是否符合契约。`Classical.choice`、`propext`、`Quot.sound` 是常用标准公理，不因出现就拒绝；`native_decide` 等原生计算可能扩大到编译器的信任边界，需披露并按认证要求选择内核路径。公理名可能随版本变化，以实际版本的官方文档为准。

specification 中作为占位的 `sorry` 可以存在，但用于认证的实现目标不能传递依赖它。`admit` 等同样不能闭合义务；自定义公理可以用于明确的条件理论，不能伪装成原题无条件证明。只做源码检查且未实际构建时只能说静态观察。

只有完整目标在声明的信任边界内检查通过、语义对应通过、当前依赖无漂移时记 `proved-formally`。形式化发现或补出的新数学证明也需纳入依赖记录；不能只更新认证标志而不更正文本。缺环境时继续数学工作或交付未认证范围，不要求为普通数学任务安装证明器。

## 定义、价值与新颖性

整体检查是诊断，不是机械锚：

- 条件定理可以是正确而有用的，但必须说明哪些桥梁尚未把条件落实到原问题。
- 只用一次的新定义可能完全合理；需问它是否让推理清晰、是否循环或买进结论，不规定“必须有两实例”。
- 已知假强命题测试只有在新陈述的合法 witness 与同一方法的实际推理都明确时才有价值；找不到这种测试就记不适用。
- 简化时给等价/蕴涵的依据，不能在简化中删除原题核心。平凡结果不必拒绝；其是否满足用户目标另判。
- 把正确性、新颖性、重要性、人类参与/工具使用分别说明；无充分检索就写“原创性未确定”，只有自评不写“已发表水准”。

## 状态使用

`proved-informally`/`proved-formally` 绑定**该陈述**与当前依赖。`disproved` 绑定满足定义的反例。实验保持 `experiment-supported`。缺口保持 `open`/`candidate`，不能用“UNDECIDABLE”暗示已证明数学不可判定；工具无结论写 `inconclusive` 即可。

示例：“L7：在 FG6 下成立，文本证明已审查；FG6：尚未从原题假设推出；P0：open。证书 E4 只覆盖 n≤5 的有限影子。” 这比“全局锚定接受=✓”提供更多且更诚实的信息。
